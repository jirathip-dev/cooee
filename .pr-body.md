## For humans

- You can ask an agent in chat to do something on a schedule ("every Monday at 9, check the renewals"). It makes a routine, and the chat shows a "Created routine" line.
- At each due time the routine sends its prompt into that chat, or starts a new thread if you asked for that. It runs once per due time, also across restarts. In the thread list it shows ⟳ and the routine's name.
- Settings › routines lists your routines with their last run. You can rename, retime, edit, pause, resume or delete them there.

## What changed

- `cooee-core/src/routines.rs` (+ the existing `routines/cron.rs`): `Routine`, `Place` (chat | new_thread), `Paused`, `Run`/`Outcome`, `make`/`edit` validation (15-minute floor, 1–60 char name, non-empty prompt, at most 50), `due()` (the newest due time past both `last_due` and `made_at`, so missed ones run once, late), the run key `routine-<id>-<due>`, and `<data>/routines.json` (0600, written whole, a newer format refused).
- `Thread.routine`, `Queued.routine`, `Body::You.routine`, the new `Body::Routine` line, `Summary.routine` (`""` for none). Every field is `serde(default)`, so old thread files load unchanged.
- `cooee-server/src/routines.rs`: the `Runner` with a 30 s tick (`date +%z` read hourly for the offset), `create` (token-checked; refused from a Workflow session or a routine's own run), `edit`/`delete`, plus the routes `POST /mcp/agent/routine`, `GET /routines`, `GET /routines.json`, `POST /routines/{id}` and `POST /routines/{id}/delete`.
- Chat runs go through `Hub::queue_as` with the routine's mark, so a busy turn queues them. `new_thread` runs use `create_later` with `Recipe.routine`, and their finished turns don't push. A chat that is closed or gone pauses the routine (`chat_gone`) with one push.
- The MCP tool `create_routine`. Web: the Settings › routines page, its Settings link, the `⟳ name` row mark, the routine line and the ⟳ mark on a routine's message in `chat.ts`.
- `router()` takes `(hub, runner)`. Its host-name list moved into `names()`, so `router` stays under clippy's 100-line limit.
- `docs/api.md`: the routes and the row field. `docs/architecture.md`: a Routines section.

Decided (routine): the prompt is a plain string with `{{due}}` replaced. The ADR's payload `Template` comes with #261, where payloads exist. `Trigger` has only `Schedule` for now. Deleting from Settings has no confirmation step, the same as removing an MCP server.

## Tests (AC 2a, AC 3)

`crates/cooee/tests/routines.rs`, through the real binary with the fake shed and the agent's real `create_routine` MCP call:
- A too-frequent schedule is refused with `BAD_SCHEDULE`. A good one adds the routine line and is listed in `/routines.json` and `/routines`.
- With `made_at` eight days back, cooee's start-up tick runs it once into the chat. The message carries the routine, the row's `routine` is its name, and shed got the prompt once.
- A restart runs nothing again (a second due routine later in the file shows that the tick finished).
- A crash between the run and its record (the test drops `last_due` and `last_run`) re-runs the same key, and the hub adopts the message already sent: still one message, and shed still got the prompt once.
- A `new_thread` routine starts its own thread, marked in the list. That thread can't make routines (`NOT_HERE`). Settings pauses it, refuses a bad schedule with 400, and deletes it, and the thread stays.
- Unit tests: due-time selection, make/edit validation, the file round trip and the newer-format refusal (core), and offset parsing (server). The cron tests are from the earlier ADR commit.
